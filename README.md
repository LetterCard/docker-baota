# 宝塔 Linux 面板容器化部署

把宝塔 Linux 面板跑在容器里，并让它**像装在物理机上一样可靠**：容器可以随意销毁、重建、换镜像，而站点、数据库、面板配置与系统环境始终留在宿主机上。

做法只有两件事：

- **面板由官方安装脚本在构建期原样装进镜像** —— 不做二次打包、不改脚本、不打补丁；
- **运行期产生的文件交给 overlay 分层接管** —— 你没动过的文件跟着镜像演进，你改过的文件留在持久化层。

由此得到的升级语义是：**换镜像即升级面板，而你改过的东西一件都不会丢。**

## 背景

在服务器上长期运行宝塔面板，会面临环境被修改、难以迁移与重建的问题。将其部署到容器中，可以隔离运行环境、便于整体备份与跨机器迁移。但容器本身是易失的，持久化方案决定了部署是否可靠。

社区中常见的两种做法存在固有局限：

- **二次打包镜像**：将面板及其依赖提前烤入镜像。这类镜像的版本取决于维护者是否跟进官方更新，来源与版本滞后，且镜像体积大、不可控。
- **整目录 bind mount**：直接将宿主机的 `/etc`、`/usr` 等系统目录挂入容器。虽然业务数据得以保留，但容器升级时这些目录被原样覆盖，新的系统配置永远无法生效，相当于把系统配置固定在了第一次启动的状态。

本项目采用另一种路径，从设计与实现上规避上述两类问题。

## 设计核心

这套方案不是「再打包一个宝塔镜像」，而是让**官方面板原样跑在容器里**的一套持久化机制，并且**项目自身几乎不需要维护**。四条原则**一条推导出下一条**：

### 不对抗上游

> **上游怎么改，我们就怎么用：不 fork、不禁用更新、不为禁用更新打补丁。**

镜像里只放运行面板所需的基础环境；面板本体由官方安装脚本**原样**安装（构建期执行），脚本取自[宝塔官网下载页](https://www.bt.cn/new/download.html)。仅有的两处构建期改动是**适配我们自己的执行入口包装**（看门狗的进程判定、面板启动幂等），不碰面板功能与面板更新，见[开发指南](docs/development.md#构建期对面板的两处适配补丁)。

面板内更新**不禁用**。想让它失效，就得把升级脚本换成 stub、再逐项跟踪上游的脚本名与代码内执行路径 —— 那条清单**永远跟不完**（上游改一个脚本名就整条失效），而面板自更新其实并不影响数据安全。所以改为**面板版本由镜像决定**：升级 / 回退就是换镜像标签，不需要 `reset-panel` 之类的维护动作；面板里点「更新」的写入也不会被执行（见下条）。

### 不可变面板

> **持久化层里存的是数据，不是代码。面板代码来自镜像 —— 改得动，但存不下。**

面板代码本身**不进持久化层，直接来自镜像层**。换镜像即升级面板；在面板里点「更新」的写入落在容器可写层，restart 不会消失，销毁重建后即还原为镜像版本。

在此基础上还有一层**执行入口守卫**：面板代码的每一次执行都先过 `/baota/guard.sh`，
发现版本与镜像不一致就用镜像里的副本换回去，**新代码从未被执行**。于是面板的 `init_db`
永远由镜像版本代码执行，持久层的库不可能「比代码新」——不存在「面板内更新过、事后换镜像
造成降级」的隐患，面板代码被更新写到一半也会在下次启动前被换回镜像版本。

这把面板版本的真源收敛到唯一一处（镜像）。也因此，**启动器恢复、版本审计等补丁都不需要**——这是「不对抗上游」换来的直接红利。

### 通用 overlay，而非定制方案

> **用内核标准能力承接系统目录，与宝塔内部实现零耦合。**

持久化用标准的 overlay 分层（lower=镜像、upper=宿主机持久层）承接系统目录（`etc usr var root opt home srv`）与 **`/www/server`**（面板里装的组件、计划任务脚本、插件数据都在它下面），业务与面板状态走 bind 直通。**整套机制与宝塔内部实现零耦合**：不依赖任何面板目录结构、不扫描面板文件、不解析面板脚本。

这意味着同一套方案对官方脚本的任意版本都成立——上游怎么改目录、怎么改安装流程，只要数据仍落在已知持久化目录内，本方案就不受影响（由每日漂移检测兜底确认）。它因此也不只是「宝塔专属」方案，而是一套通用的系统目录持久化方法。

### 不用维护项目

> **没有要同步的补丁清单，没有要跟进的上游代码路径。**

以上三条叠加，结果是**项目本身几乎没有持续维护成本**：没有要同步的补丁清单、没有要跟进的上游代码路径、没有要 rebase 的 fork。维护者要做的只是「盯住上游是否把数据写到了已知持久化目录之外」（漂移检测每天自动完成），确认无异常后手动触发发布即可。

由此得到的关键能力：镜像可随时替换以升级系统配置与面板，而用户产生的配置、站点与数据库始终留在宿主机上；升级语义等价于物理机上 `apt upgrade` 后再换一套面板程序。

## 工作原理

### 镜像与首次启动

面板已在**构建期**由官方安装脚本装进镜像（不可变面板，见[设计核心](#设计核心)）。
容器启动时 entrypoint 检查持久化数据是否为首次使用，只做**一次性初始化**（不重装面板）：

- 随机生成面板安全入口、面板口令与容器内 root 口令（覆盖构建期占位值），仅在首启日志打印；
- 记录镜像版本与面板代码指纹到持久化层，作为升级判断的依据；此后每次启动比对，
  变化（升级 / 回退）时先对面板状态做快照；
- 持久化根只读或挂载失败时写 `critical`，健康检查判 unhealthy，而不是静默写入失败。

数据已存在则跳过初始化，直接复用已有配置与凭据。

### 持久化模型

只挂一个 `./data:/data`。**规则只有一条：`data/www` 下的路径 = 容器内的路径**，
找什么按容器里的路径找（完整表格见[持久化原理](docs/persistence.md)）：

```
data/
├── www/          业务与面板状态（bind，宿主机可直接读写、可直接拷贝迁移）
│   ├── wwwroot/         站点            ↔ /www/wwwroot
│   ├── backup/          备份            ↔ /www/backup
│   ├── server/data/     MySQL 数据      ↔ /www/server/data
│   ├── server/panel/    面板状态        ↔ /www/server/panel（只持久化下列子目录）
│   │   ├── data/ plugin/ vhost/ ssl/ config/
│   │   │                配置与 SQLite / 插件 / 站点配置与证书 / 面板证书 / 面板设置
│   │   └── pyenv/       pyenv 覆盖层 upper ↔ 插件 pip 装的包（解释器本身仍来自镜像）
│   ├── vmail/           邮局数据        ↔ /www/vmail（装了邮局才出现）
│   └── dk_project/      面板 Docker 项目 ↔ /www/dk_project（装了 Docker 模块才出现）
├── .system/      系统层（overlay upper，隐藏：是相对镜像的改动）
│   ├── etc usr var root opt home srv     系统目录
│   ├── www/server/                       面板里装的组件、计划任务脚本、插件数据
│   └── .baota/                           锁 / 版本与指纹记录 / 启动历史
└── .baota/       数据层元数据（并发锁，隐藏）
```

**面板代码**（`/www/server/panel`）**不持久化**：它属于镜像，随镜像替换整体更新
（`init.sh` 在挂 `/www/server` 的 overlay 之前先把面板目录 bind 到 `/run`，
挂完再 bind 回来，所以面板代码不落持久化层，面板里装的东西照常持久化）。
在面板里点「更新」的写入落在容器可写层，销毁重建后即还原为镜像版本 ——
升级面板请换镜像标签。面板版本只有一个真源（镜像），
启动器恢复、版本审计之类的补丁也就都不需要了。

**pyenv 覆盖层**：面板的 Python 环境走一层独立 overlay —— `pip` 装进来的包落在
`data/www/server/panel/pyenv`（重建后还在），解释器与镜像自带依赖仍来自镜像
（换镜像照常更新）。于是「插件重建后还能跑」不再依赖把 `pyenv` 整个持久化。

**执行入口守卫**：面板更新写进来的新代码**不会被执行** —— 面板代码的每次执行
都先过 `/baota/guard.sh`，发现代码版本 ≠ 镜像版本就用镜像副本换回去（只覆盖、
不删除，异常一律放行）。于是面板内点「更新」在 UI 上仍显示成功，但新代码从未生效；
面板的 `init_db` 永远由镜像版本代码执行，**持久层的库不可能「比代码新」**。
实现细节见[持久化原理](docs/persistence.md#执行入口守卫不可变面板的兜底)。

### 升级语义

「换镜像」= 升级系统配置 + 升级面板：overlay 里没改过的文件跟新镜像走、改过的留在
upper；业务数据、面板状态、面板里装的组件都是持久的，完全不动。
完整取舍与实测见[持久化原理](docs/persistence.md#换镜像后会发生什么)。

### 并发与一致性保护

持久化层在挂载时获取排他锁。当同一份持久化数据被第二个容器实例尝试挂载时，锁竞争会阻止其启动，避免两个实例同时写入同一份数据造成损坏。

## 快速开始

环境要求三条，缺一不可：

- 已安装 Docker 与 Docker Compose；
- 持久化根（`/data`、`/data/.system`）必须位于 **ext4、btrfs 或 xfs** 上（飞牛存储池满足）；
  落在 SMB / NFS / exFAT / NTFS 上会「挂载成功但只读」、写入**静默失败** ——
  这是唯一的硬要求，绕法见[系统层 ext4 镜像兜底](docs/persistence.md#系统层-ext4-镜像兜底opt-in)；
- 容器以**特权模式**运行（`docker-compose.yml` 已配好），因此不适用于 rootless Docker。

资源：镜像约 1.4–1.8 GB（两条线不同）；面板、MySQL 与 PHP 会常驻，建议宿主机内存 ≥ 2 GB
（建站后按需增加）。

```bash
cd baota-docker                   # 仓库根目录（docker-compose.yml 就在这里）
docker compose up -d
docker compose logs -f baota      # 面板地址、账号与口令只在首次启动时打印在这里
```

凭据请登录后立即修改，面板地址格式为 `http://<宿主机IP>:8888/<安全入口>/login`。
飞牛 NAS 的图形界面步骤、端口避让与 `.env` 写法见[快速开始](docs/quickstart.md)。

项目维护两条发布线（12/13），**全部差异只写在一张声明表里**
（[image/lines.conf](image/lines.conf)，12/13 的安装脚本地址成对排列；
Dockerfile 与流水线都只有一份）：

| 线标识 | 显示名 | 上游脚本 | 标签 | 适合 |
|---|---|---|---|---|
| `12_version` | `12.x` | `installStable_12.sh`（稳定线） | 仅精确版本 | 追求稳定的生产环境 |
| `13_version` | `13.x` | `install_panel.sh`（最新正式版） | 版本 + `latest` | 希望及时用上新版 |

新增一条线（14/15/…）或上游换稳定线，都只是改这张表；细节见[发布流程](docs/release.md)。

> **`pro` 线已完全独立**：它不在上面的声明表里，而是拥有专属的
> [Dockerfile](image/versions/pro/Dockerfile) 与专属发布流水线
> [`.github/workflows/build-pro.yml`](.github/workflows/build-pro.yml)，
> 授权补丁在 [image/versions/pro/build/patch_pro_license.sh](image/versions/pro/build/patch_pro_license.sh)。
> 12/13 线的任何改动都不会触发 pro 的构建，反之亦然。
> `pro` 是**静态线**：安装脚本来自第三方 `baota.1000.run`（拉 `panel6.zip`，版本不透明、无标准版本号），
> 故跳过版本探测与每日漂移检测，只手动触发构建；发布标签固定为字面量 `pro`（不随版本号、也不发 `latest`），
> 由 `build-pro.yml` 的四套门禁在手动构建时覆盖。

各线**均为手动发布**（不定时自动发布）：发布前先看[漂移检测](docs/development.md#漂移检测)报告，
确认无关键漂移后再手动触发，避免上游一出问题就被自动分发。已发布的镜像仍每天回归验证
（`pro` 静态线除外，见上）。

## 常见操作

以下操作的具体步骤与注意事项在文档中单独说明：

- **备份与迁移**：对 `/data` 整体备份或跨机器迁移；

详见 [升级与迁移](docs/upgrade.md) 及[文档地图](#文档地图)里的对应章节。

## 与常见方案的差异

在容器中部署宝塔，不同方案的主要差异在于持久化方式：

| 方案 | 镜像来源 | 镜像升级 | 数据保留 |
|---|---|---|---|
| 官方脚本直装物理机 | 官方 | 原生 | 原生 |
| 社区二次打包镜像 | 社区集成依赖 | 依赖打包者维护 | 取决于打包质量 |
| 整目录 bind mount | 官方脚本 | 配置被固定为首启状态，升级失效 | 业务数据可保留 |
| 本项目（不可变面板 + 分层持久化） | 官方脚本 | 系统配置与面板均随镜像更新 | 业务、面板状态与系统配置均保留 |

整目录 bind mount 直接挂载 `/etc`、`/usr` 等系统目录，会使镜像升级在这些目录上失效；
本项目只把用户修改保留在持久化层，其余随镜像更新，而面板代码整体来自镜像，
因此升级镜像即同时更新系统配置与面板。详细取舍与实测数据见
[持久化原理](docs/persistence.md#为什么用-overlay-而不是整目录-bind)。

## 限制与风险

以下都是**设计取舍的结果**，不是待修的缺陷。部署前请确认都能接受：

- **面板内「更新」不会生效**。写入落在容器可写层，且执行入口守卫会在代码被执行前换回镜像版本（UI 仍会显示「更新成功」）。升级 / 回退面板请换镜像标签。
- **不支持 rootless Docker 与无特权的托管容器服务**。overlay 挂载与 systemd 都要求特权模式；它的取舍、安全影响与规避清单见[特权模式（privileged）的取舍与规避](#特权模式privileged的取舍与规避)。
- **持久化根不能是网络文件系统**。SMB / NFS / exFAT / NTFS 会「挂载成功但只读」，写入静默失败 —— 这是最危险的失效模式，启动时会被识别为 `critical` 并判 unhealthy。唯一的绕法是 opt-in 的[系统层 ext4 镜像兜底](docs/persistence.md#系统层-ext4-镜像兜底opt-in)：把系统层装进 data 卷里的一个镜像文件，业务层不受影响。
- **同一份 `data/` 不能被两个容器同时挂载**。挂载时取排他锁，第二个实例会被阻止启动（避免并发写坏数据）；12.x 与 13.x 若指向同一个 `data/` 目录就会触发。
- **跨架构搬移 `data/` 未经验证**。amd64 与 arm64 各自构建镜像，同一份 `data/` 在两种架构之间迁移不在门禁覆盖范围内。

## 特权模式（privileged）的取舍与规避

`docker-compose.yml` 里用了 `privileged: true` 加 `security_opt: [seccomp:unconfined, apparmor:unconfined]`。
这不是图省事，而是被本方案的三项硬需求共同决定的；下面说清它换来什么、代价是什么、以及怎么把代价压到最低。

### 为什么必须 privileged

| 需求 | 需要的特权 | 不授权会怎样 |
|---|---|---|
| 运行期 `mount -t overlay` 接系统目录 | `CAP_SYS_ADMIN` | 持久化层挂不上，写入落到容器可写层、重建即丢 |
| 把业务/状态子目录 `mount -o bind` 进 `/www` | `CAP_SYS_ADMIN` | 同上 |
| 以 systemd 作 PID1（停 nginx/MySQL/面板靠它） | `CAP_SYS_ADMIN` + 可写 `/sys/fs/cgroup` + `/run` tmpfs | 起不来或关机超时被强杀 |
| 宝塔管服务、跑 `iptables`/防火墙 | `CAP_NET_ADMIN` | 面板里装软件、改防火墙失败 |
| opt-in 的 ext4 镜像兜底（`PERSIST_SYSTEM_IMAGE`）挂 loop 设备 | `/dev/loop-control` + loop 设备节点 | 兜底模式挂不上盘 |

逐项授权能做到，但要把上面这些 capability、设备节点、以及 systemd 依赖的 seccomp/apparmor 放开
凑齐，几乎等于把 `privileged` 该给的都给了——这也是 compose 直接写 `privileged` 而不是一长串
`cap_add` 的原因：更短、更不容易漏，且四套 CI 门禁（功能 / 降级 / 升级 / 恢复）都只在 privileged
下验证过。

### 安全影响

`privileged` 等价于**把宿主机内核交给容器**：它拿到全部 Linux capabilities，能读写所有 `/dev`、
加载内核模块、改宿主机 iptables、触及宿主网络命名空间。换言之，容器内一旦被攻破
（来路不明的面板插件、站点里跑的 PHP 代码被利用，或镜像本身不可信），攻击者就约等于拿到了宿主机 root。

所以这一条是**设计取舍，不是缺陷**，前提是「容器跑在可信边界内」。它不适合：

- 多租户 / 共享的托管 Docker 服务（rootless 也不行，见上）；
- 把 Docker socket 挂进容器的玩法；
- 把面板、SSH、phpMyAdmin 端口直接暴露到公网。

### 规避风险的清单

1. **只在自己信任的内网 / 单机跑**，最好是独占的 NAS 或虚拟机，不与不可信负载混部。
2. **端口别曝公网**：SSH（`2222`）非必要注释掉；phpMyAdmin（`888`）默认开放，不用就注释；
   面板安全入口（随机 8 位）务必保留，别把 `/login` 直曝公网。
3. **首启凭据默认随机生成、只在首次启动日志里打印**（看 `docker compose logs`），登录后立刻在面板里重设。
   想固定口令时：把 `PANEL_PASSWORD`/`ROOT_PASSWORD` 等写进同目录的 `.env`，**不要直接写进 `docker-compose.yml` 再提交到 Git**（那会把口令进版本库）。
   只拉镜像本地跑、不提交仓库的，用随机口令 + 面板内重设即可，无需 `.env`。
4. **不在面板里装来路不明的插件、跑不可信的站点代码**——特权模式下它们等同宿主 root 权限。
5. **设 `mem_limit`**：把故障域封在容器内，避免 MySQL 失控拖垮整机（见[编排配置详解](docs/configuration.md#资源上限与规划)）。
6. **定期 `docker compose ps` 看 STATUS**：持久化降级会直接 `unhealthy`，别等数据静默丢才发现。

### 想缩小攻击面：capability 最小化（备选，未经 CI 验证）

若你接受「非特权化需自行验证、且失去部分能力」的代价，可把 `privileged: true` 换成：

```yaml
    # 去掉 privileged，改为最小授权；systemd + overlay + 宝塔服务管理都靠这些
    cap_drop:
      - ALL             # 必须先行：否则 Docker 默认的 ~14 个 cap（MKNOD / DAC_OVERRIDE /
                        # NET_RAW…）仍在，缩小的是假象
    cap_add:
      - SYS_ADMIN      # mount overlay / bind、systemd
      - SYS_RESOURCE   # systemd 设置资源上限
      - NET_ADMIN      # 宝塔 iptables / 防火墙
    security_opt:
      - apparmor:unconfined
      - seccomp:unconfined
    devices:
      - /dev/loop-control   # 仅启用 PERSIST_SYSTEM_IMAGE 兜底时才需要
      - /dev/loop0
```

实测（OrbStack 上只能验证能力位，overlay 被其运行时整体禁止，见下方）：`cap_drop: ALL` + 三项 `cap_add` 后
容器内 `CapEff = 0000000001201000`，恰好只有 `SYS_ADMIN + SYS_RESOURCE + NET_ADMIN` 三位，
`mknod` 创建设备节点等默认危险操作已被拒；去掉 `cap_drop: ALL` 时会多出 Docker 默认那批 cap，缩小大打折扣。

注意：

- 这**没有消除**核心风险——`SYS_ADMIN` 已是内核级权限，仍等价于很大一部分 privileged；
  它只是不再开放「所有设备 + 所有 capability + 内核模块加载」这一整包。
- loop 镜像兜底（`PERSIST_SYSTEM_IMAGE`）必须额外挂 `/dev/loop*`，否则该模式挂不上。
- 此路径**未经过本项目的 CI 门禁**（core/degrade/upgrade/restore 都在 privileged 下验证），
  不同宿主机（cgroup v1/v2、Docker 版本、AppArmor 配置）表现可能不一致，出问题需自行排查。
- ⚠️ **不要拿 OrbStack / 其他 macOS 容器运行时当验证环境**：实测其运行时整体禁止在容器内挂
  overlayfs（连 `privileged` 都报 `wrong fs type / bad superblock`），systemd 在非特权容器里也起不来；
  这与「macOS 宿主目录不是 ext4/btrfs/xfs」是同一类硬约束的更彻底版本。最小集只在**真实 Linux 宿主**
  （飞牛 / Debian / Ubuntu）上才有意义，且仍需你在那上面亲自验证。
- 真要降到最低风险，更彻底的做法是**把容器放到独立、不存其他敏感数据的宿主机上**，
  而不是在 capability 上微调——隔离边界比权限裁剪更可靠。

> 结论：**默认保持 `privileged`**（项目支持且 CI 覆盖的路径）；上面的最小化方案仅作为
> 你已评估过风险、且愿意自行维护时的可选项。两者都不解决「容器被攻破=宿主受威胁」这一根本问题，
> 那只能靠前面的风险清单与网络隔离来兜底。

## 健康检查与每日验证

容器内置健康检查，监控面板与 systemd 的就绪状态；在 `critical` 等异常状态下会判定为 unhealthy，便于编排系统及时发现。

### 部署后自检（验收）

`docker compose up -d` 之后按顺序确认这四条，全过才算部署成功：

1. `docker compose ps` 里容器状态为 `healthy`（unhealthy 意味着持久化降级或磁盘水位告警，先看日志里的降级原因）；
2. 打开 `http://<宿主机IP>:8888/<安全入口>/login`，用首次启动日志里的凭据登录；
3. 建一个测试站点、在面板里装一个组件，然后 `docker compose down && docker compose up -d` 重建，确认站点与组件都还在；
4. 执行 `docker exec baota baota-backup` 确认备份产出 —— 并按[备份与恢复](docs/backup.md)演练一次恢复（能打出来不等于能恢复）。

开发者还可在候选镜像上自动验这些承诺：`make build && make health-all`
（四套门禁：功能 / 只读降级 / 版本演进 / 备份恢复）；已发布镜像每天再回归一轮，
复用同一套门禁。两者覆盖的断言清单见[开发指南](docs/development.md#发布前检查覆盖什么)，
每日结果由 CI 自动生成并维护，见下方报告。

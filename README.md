# 宝塔 Linux 面板容器化部署

本项目将宝塔 Linux 面板以容器方式运行。镜像在**构建期**通过官方安装脚本**原样**完成面板安装（不做二次打包、不加补丁），并以 overlay 分层方式对运行时产生的文件进行持久化，使面板在容器销毁、重建或升级镜像后仍能保留业务数据与系统配置。

目标是在容器环境中获得接近物理机安装的体验：面板版本随镜像演进，数据不依赖容器生命周期，升级行为与原生系统的软件更新一致。

## 背景

在服务器上长期运行宝塔面板，会面临环境被修改、难以迁移与重建的问题。将其部署到容器中，可以隔离运行环境、便于整体备份与跨机器迁移。但容器本身是易失的，持久化方案决定了部署是否可靠。

社区中常见的两种做法存在固有局限：

- **二次打包镜像**：将面板及其依赖提前烤入镜像。这类镜像的版本取决于维护者是否跟进官方更新，来源与版本滞后，且镜像体积大、不可控。
- **整目录 bind mount**：直接将宿主机的 `/etc`、`/usr` 等系统目录挂入容器。虽然业务数据得以保留，但容器升级时这些目录被原样覆盖，新的系统配置永远无法生效，相当于把系统配置固定在了第一次启动的状态。

本项目采用另一种路径，从设计与实现上规避上述两类问题。

---

## 设计核心

本项目不是「再打包一个宝塔镜像」，而是一套**让官方面板原样跑在容器里、且项目自身几乎零维护**的持久化方案。四条原则互相支撑：

### 不对抗上游

镜像里只放运行面板所需的基础环境；面板本体由官方安装脚本**原样**安装（构建期执行，不加补丁、不改脚本、不禁用面板更新、不 fork 任何上游逻辑），脚本取自[宝塔官网下载页](https://www.bt.cn/new/download.html)。

我们曾经为了「让面板内更新失效」内置过一套补丁——把升级脚本替换成 stub，并逐项跟踪上游的脚本名与代码内执行路径。实测它**永远跟不完**：上游改一个脚本名整条清单就失效，而且面板自更新并不影响数据安全。于是整体移除，改为**面板版本由镜像决定**——想升级 / 回退就换镜像标签，不需要 `reset-panel` 之类的维护动作。

### 不可变面板

面板代码本身**不进持久化层，直接来自镜像层**。换镜像即升级面板；在面板里点「更新」的写入落在容器可写层，restart 不会消失，销毁重建后即还原为镜像版本。

在此基础上还有一层**执行入口守卫**：面板代码的每一次执行都先过 `/baota/guard.sh`，
发现版本与镜像不一致就用镜像里的副本换回去，**新代码从未被执行**。于是面板的 `init_db`
永远由镜像版本代码执行，持久层的库不可能「比代码新」——不存在「面板内更新过、事后换镜像
造成降级」的隐患，面板代码被更新写到一半也会在下次启动前被换回镜像版本。

这把面板版本的真源收敛到唯一一处（镜像）。也因此，**启动器恢复、版本审计等补丁都不需要**——这是「不对抗上游」换来的直接红利。

### 通用 overlay，而非定制方案

持久化用标准的 overlay 分层（lower=镜像、upper=宿主机持久层）承接系统目录（`etc usr var root opt home srv`）与 **`/www/server`**（面板里装的组件、计划任务脚本、插件数据都在它下面），业务与面板状态走 bind 直通。**整套机制与宝塔内部实现零耦合**：不依赖任何面板目录结构、不扫描面板文件、不解析面板脚本。

这意味着同一套方案对官方脚本的任意版本都成立——上游怎么改目录、怎么改安装流程，只要数据仍落在已知持久化目录内，本方案就不受影响（由每日漂移检测兜底确认）。它因此也不只是「宝塔专属」方案，而是一套通用的系统目录持久化方法。

### 不用维护项目

以上三条叠加，结果是**项目本身几乎没有持续维护成本**：没有要同步的补丁清单、没有要跟进的上游代码路径、没有要 rebase 的 fork。维护者要做的只是「盯住上游是否把数据写到了已知持久化目录之外」（漂移检测每天自动完成），确认无异常后手动触发发布即可。

---

由此得到的关键能力：镜像可随时替换以升级系统配置与面板，而用户产生的配置、站点与数据库始终留在宿主机上；升级语义等价于物理机上 `apt upgrade` 后再换一套面板程序。

## 工作原理

### 镜像与首次启动

面板已在**构建期**由官方安装脚本装进镜像（不可变面板，见[设计核心](#设计核心)）。容器启动时，entrypoint 只检查持久化数据是否为首次使用，并做**一次性初始化**（不重装面板）：

- 随机生成面板账号、面板口令与容器内 root 口令（非构建期占位值），仅在首次启动时打印；
- 记录当前镜像版本到持久化层，作为后续升级判断的依据；
- 应用运行期配置（版本护栏、升级前快照、日志交由宝塔面板处理等）。

若持久化数据已存在，则跳过初始化，直接复用已有配置与凭据。

### 持久化模型

只挂一个 `./data:/data`，三层分清楚（完整表格见[持久化原理](docs/persistence.md)）：

```
data/
├── www/          业务数据（bind，宿主机可直接 SMB 读写）
│   ├── wwwroot/       站点            ↔ /www/wwwroot
│   ├── backup/        备份            ↔ /www/backup
│   ├── Recycle_bin/   面板回收站       ↔ /www/Recycle_bin
│   └── server/data/   MySQL 数据       ↔ /www/server/data
├── panel/        面板状态（bind）
│   └── data/ plugin/ vhost/ ssl/ config/
│                      配置与 SQLite / 插件 / 站点配置与证书 / 面板证书 / 面板设置
└── system/       系统层（overlay upper）
    ├── etc usr var root opt home srv     系统目录
    ├── www/server/                       面板里装的组件、计划任务脚本、插件数据
    └── .baota/                           锁 / 镜像版本记录 / 启动历史
```

**面板代码**（`/www/server/panel`）**不持久化**：它属于镜像，随镜像替换整体更新
（`init.sh` 在挂 `/www/server` 的 overlay 之前先把面板目录 bind 到 `/run`，
挂完再 bind 回来，所以面板代码不落持久化层，面板里装的东西照常持久化）。

**面板代码**（`/www/server/panel`）**不持久化**：它属于镜像，随镜像替换整体更新
（`init.sh` 在挂 `/www/server` 的 overlay 之前先把面板目录 bind 到 `/run`，
挂完再 bind 回来，所以面板代码不落持久化层，面板里装的东西照常持久化）。
在面板里点「更新」的写入落在容器可写层，销毁重建后即还原为镜像版本 ——
升级面板请换镜像标签。面板版本只有一个真源（镜像），
启动器恢复、版本审计之类的补丁也就都不需要了。

**执行入口守卫**：面板更新写进来的新代码**不会被执行** —— 面板代码的每次执行
都先过 `/baota/guard.sh`，发现代码版本 ≠ 镜像版本就用镜像副本换回去。因此：

- 面板内点「更新」在 UI 上仍显示成功，但新代码从未生效，重启/重建后仍是镜像版本；
- 面板的 `init_db` 永远由镜像版本的代码执行，**持久层的库不可能「比代码新」**，
  也就不会出现「面板内更新过、后来换了更旧镜像」的降级组合；
- 面板代码被写坏（更新到一半）也会在下次启动前被换回镜像版本；
- 只覆盖、不删除：运行期新增的文件（如 `class/404_settings.json`）保留。

实现细节（守卫的三条铁律、排除项、fail-open）见
[持久化原理](docs/persistence.md#执行入口守卫不可变面板的兜底)。

### 升级语义

「换镜像」= 升级系统配置 + 升级面板：overlay 里没改过的文件跟新镜像走、改过的留在
upper；业务数据、面板状态、面板里装的组件都是持久的，完全不动。
完整取舍与实测见[持久化原理](docs/persistence.md#换镜像后会发生什么)。

### 并发与一致性保护

持久化层在挂载时获取排他锁。当同一份持久化数据被第二个容器实例尝试挂载时，锁竞争会阻止其启动，避免两个实例同时写入同一份数据造成损坏。

### 启动期维护

entrypoint 只在**首次启动**（`data/` 为空）时做一次性初始化：

- 首启随机生成面板安全入口、面板口令与 root 口令（覆盖镜像构建期的占位值）；
- 记录镜像版本；此后每次启动比对版本，变化（升级 / 回退）时先对面板状态做快照；
- 持久化根只读或挂载失败时写 `degraded-critical`，健康检查判 unhealthy，而不是静默写入失败。

## 快速开始

### 环境要求

- 已安装 Docker 与 Docker Compose；
- 持久化根（`/data`、`/data/system`）必须位于 **ext4、btrfs 或 xfs** 文件系统上（飞牛存储池满足此要求）。

  > 若持久化根落在 SMB、NFS、exFAT 或 NTFS 上，挂载会成功但表现为只读，写入将静默失败。这是本项目的唯一硬要求。

### 启动

```bash
cd baota-docker                   # 仓库根目录（docker-compose.yml 就在这里）
docker compose up -d
docker compose logs -f baota   # 首次登录信息在此输出
```

### 首次启动后

首次启动时，面板地址、面板账号与口令会在日志中打印一次：

```bash
docker compose logs baota
```

上述凭据只在首次启动时输出，请登录面板后立即修改。面板地址格式为 `http://<宿主机IP>:8888/<安全入口>/login`。

## 与常见方案的差异

在容器中部署宝塔，不同方案的主要差异在于持久化方式：

| 方案 | 镜像来源 | 镜像升级 | 数据保留 |
|---|---|---|---|
| 官方脚本直装物理机 | 官方 | 原生 | 原生 |
| 社区二次打包镜像 | 社区集成依赖 | 依赖打包者维护 | 取决于打包质量 |
| 整目录 bind mount | 官方脚本 | 配置被固定为首启状态，升级失效 | 业务数据可保留 |
| 本项目（不可变面板 + 分层持久化） | 官方脚本 | 系统配置与面板均随镜像更新 | 业务、面板状态与系统配置均保留 |

整目录 bind mount 直接挂载 `/etc`、`/usr` 等系统目录，会使镜像升级在这些目录上失效；
本项目只把用户修改保留在持久化层，其余随镜像更新，而面板代码整体来自镜像，
因此升级镜像即同时更新系统配置与面板。详细取舍与实测数据见
[持久化原理](docs/persistence.md#为什么用-overlay-而不是整目录-bind)。

## 健康检查与每日验证

容器内置健康检查，监控面板与 systemd 的就绪状态；在 `degraded-critical` 等异常状态下会判定为 unhealthy，便于编排系统及时发现。

已发布镜像每日做一轮回归：拉取线上镜像、留一段脱敏后的首启日志、在真镜像上真编译一个 PHP 扩展，
并**复用发布前的三套门禁**（功能 / 只读降级 / 版本演进）—— 覆盖首次启动、持久化落盘、
重建、并发锁、升级降级等全部承诺。入口见 `.github/scripts/check/published.sh`，
检查结果由每日 CI 自动生成并维护，见下方报告。

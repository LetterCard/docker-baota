# 宝塔 Linux 面板容器化部署

本项目将宝塔 Linux 面板以容器方式运行。镜像在容器首次启动时通过官方安装脚本完成面板安装，并以 overlay 分层方式对运行时产生的文件进行持久化，使面板在容器销毁、重建或升级镜像后仍能保留业务数据与系统配置。

目标是在容器环境中获得接近物理机安装的体验：面板版本随镜像演进，数据不依赖容器生命周期，升级行为与原生系统的软件更新一致。

## 背景

在服务器上长期运行宝塔面板，会面临环境被修改、难以迁移与重建的问题。将其部署到容器中，可以隔离运行环境、便于整体备份与跨机器迁移。但容器本身是易失的，持久化方案决定了部署是否可靠。

社区中常见的两种做法存在固有局限：

- **二次打包镜像**：将面板及其依赖提前烤入镜像。这类镜像的版本取决于维护者是否跟进官方更新，来源与版本滞后，且镜像体积大、不可控。
- **整目录 bind mount**：直接将宿主机的 `/etc`、`/usr` 等系统目录挂入容器。虽然业务数据得以保留，但容器升级时这些目录被原样覆盖，新的系统配置永远无法生效，相当于把系统配置固定在了第一次启动的状态。

本项目采用另一种路径，从设计与实现上规避上述两类问题。

---

## 设计思路

核心原则只有两条：

1. **镜像不做二次打包**。镜像只提供运行面板所需的基础环境，面板本身由官方安装脚本在首次启动时安装。镜像内容完全来自官方脚本，脚本取自[宝塔官网下载页](https://www.bt.cn/new/download.html)。
2. **用 overlay 分层做持久化**。容器运行时所有会变化的文件，按「系统层」与「数据层」分别落到宿主机的持久化目录，而非整目录挂载。

由此带来的直接结果是：镜像可以随时替换以升级面板，而用户产生的配置与数据始终保存在宿主机上。

## 工作原理

### 镜像与首次启动

容器启动时，entrypoint 检查持久化数据是否为首次使用。若为空，则执行官方安装脚本安装宝塔，并随即完成以下初始化：

- 随机生成面板账号、面板口令与容器内 root 口令（非构建期占位值），仅在首次启动时打印；
- 记录当前镜像版本到持久化层，作为后续升级判断的依据；
- 应用维护补丁（见下文）。

若持久化数据已存在，则跳过安装，直接复用已有配置与凭据。

### 持久化模型

持久化分为两层，分别位于宿主机的 `/data/system` 与 `/data/www`。

**系统层**（`/data/system`）以 overlay 方式承接系统目录的写操作，保存面板与系统产生的配置变更：

| 容器内路径 | 持久化位置 | 说明 |
|---|---|---|
| `/www` | `/data/system/panel` | 面板程序与运行数据 |
| `/etc` | `/data/system/etc` | 系统与服务配置 |
| `/usr` | `/data/system/usr` | 程序与库 |
| `/var` | `/data/system/var` | 变量数据（含计划任务等） |
| `/root` | `/data/system/root` | root 用户目录 |
| `/opt` | `/data/system/opt` | 附加软件 |
| `/home` | `/data/system/home` | 用户目录 |
| `/srv` | `/data/system/srv` | 服务数据 |

**数据层**（`/data/www`）以直通方式挂载，保存用户业务数据，避免大文件经过 overlay 层带来的性能与一致性开销：

| 容器内路径 | 持久化位置 | 说明 |
|---|---|---|
| `/www/wwwroot` | `/data/www/wwwroot` | 网站根目录 |
| `/www/backup` | `/data/www/backup` | 备份文件 |
| `/www/server/data` | `/data/www/server/data` | 数据库数据 |

### 升级语义

升级镜像时，overlay 的 upper 层仅包含用户修改过的文件。未被修改的文件随新镜像（lower 层）更新，只有用户实际改动过的文件保留在持久化层并覆盖于其上。

这一机制使「升级镜像」在语义上等价于「升级系统配置」：新镜像带来的配置与程序变更能够生效，而用户的个性化修改不会被覆盖。这与在物理机上执行 `apt upgrade` 后再安装软件的行为一致，也避免了 bind mount 方案中系统目录被整目录钉死的问题。

### 并发与一致性保护

持久化层在挂载时获取排他锁。当同一份持久化数据被第二个容器实例尝试挂载时，锁竞争会阻止其启动，避免两个实例同时写入同一份数据造成损坏。

### 安全与维护补丁

首次启动后，entrypoint 会应用若干维护性修改，使面板更适合容器长期运行：

- 替换面板内的更新入口脚本并关闭自动更新，确保面板版本由镜像统一控制，而非在面板内点选升级；
- 写入 journald 体积上限配置（总占用不超过 200M，保留 7 天）；
- 生成日志轮转配置（面板日志保留 7 份，站点日志保留 14 份）。

> 边界说明：以上补丁只能挡住经由面板 `script/` 目录的更新入口。面板代码里另有 3 处
> 「现拉官方更新脚本直接执行」的路径，本项目不改面板代码、不在此层阻断，由每次启动的
> 版本一致性检测兜底发现——若启动日志出现「面板实际版本与镜像版本不一致」，
> 执行 `make reset-panel CONFIRM=yes` 把面板代码重置回镜像版本即可。
> 旁路明细与可选的网络层加固见 `docs/development.md`「禁用面板更新的防御边界」。

当持久化根被挂载为只读（例如落在不支持的远程文件系统上）时，系统会将其标记为 `degraded-critical`，并使健康检查判定为 unhealthy，而不是静默写入失败。

## 快速开始

### 环境要求

- 已安装 Docker 与 Docker Compose；
- 持久化根（`/data`、`/data/system`）必须位于 **ext4、btrfs 或 xfs** 文件系统上（飞牛存储池满足此要求）。

  > 若持久化根落在 SMB、NFS、exFAT 或 NTFS 上，挂载会成功但表现为只读，写入将静默失败。这是本项目的唯一硬要求。

### 启动

```bash
cd stable              # 或 release，见「发布通道」
docker compose up -d
docker compose logs -f baota   # 首次登录信息在此输出
```

### 首次启动后

首次启动时，面板地址、面板账号与口令会在日志中打印一次：

```bash
docker compose logs baota
```

上述凭据只在首次启动时输出，请登录面板后立即修改。面板地址格式为 `http://<宿主机IP>:8888/<安全入口>/login`。

## 发布通道

项目维护两个发布通道，面向不同的更新节奏需求：

- **`stable`**：跟进宝塔稳定线 12.x，仅发布精确版本标签，不提供 `latest`。适合追求稳定的生产环境。
- **`release`**：跟进正式版，提供 `latest` 标签。适合希望及时获得新版面的场景。

两个通道**均为手动发布**（不定时自动发布）：发布前先看[漂移检测](docs/development.md#漂移检测)报告，
确认无关键漂移后再手动触发，避免上游一出问题就被自动分发。已发布的镜像仍每天回归验证。

## 常见操作

以下操作的具体步骤与注意事项在文档中单独说明：

- **升级镜像**：替换镜像标签并重新创建容器，数据不受影响；
- **备份与迁移**：对 `/data` 整体备份或跨机器迁移；
- **重建容器**：销毁后使用同一份持久化数据重建，凭据与数据保持不变；
- **排障**：查看日志、健康检查状态与已知问题。

详见 [升级与迁移](docs/upgrade.md) 及 [docs/](docs/README.md) 下的对应章节。

## 与常见方案的差异

在容器中部署宝塔，不同方案的主要差异在于持久化方式：

| 方案 | 镜像来源 | 镜像升级 | 数据保留 |
|---|---|---|---|
| 官方脚本直装物理机 | 官方 | 原生 | 原生 |
| 社区二次打包镜像 | 社区集成依赖 | 依赖打包者维护 | 取决于打包质量 |
| 整目录 bind mount | 官方脚本 | 配置被固定为首启状态，升级失效 | 业务数据可保留 |
| 本项目（overlay 分层） | 官方脚本 | 有效 | 业务与系统配置均保留 |

整目录 bind mount 直接挂载 `/etc`、`/usr` 等系统目录，会使镜像升级在这两个目录上失效；本项目仅将用户修改的文件保留在持久化层，其余随镜像更新，因此升级镜像即更新系统配置。详细取舍与实测数据见 [持久化方案选型](docs/alternatives.md)。

## 健康检查与每日验证

容器内置健康检查，监控面板与 systemd 的就绪状态；在 `degraded-critical` 等异常状态下会判定为 unhealthy，便于编排系统及时发现。

已发布镜像每日执行 19 项功能回归检查，覆盖首次启动、持久化落盘、重建、升级、降级与并发锁等关键路径。检查结果由每日 CI 自动生成并维护，见下方报告。
